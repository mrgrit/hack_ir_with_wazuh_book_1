REV02 복사용 입력 — 본문의 선행 조건과 원상복구 절차를 확인하고 한 블록씩 사용한다.

[C10-01] kt66 VM · ccc 호스트 셸
조사할 호스트와 시각을 기록하고 필요한 도구·수집 서비스가 준비됐는지 확인한다.
hostname은 현재 컴퓨터 이름, date -Is는 시간대가 포함된 시각을 출력한다. command -v는 명령의 위치를 찾는다. systemctl is-active는 서비스의 현재 실행 상태를 확인한다.
hostname
date -Is
command -v nc ss netstat osqueryi
systemctl is-active wazuh-agent osqueryd
확인: 호스트 이름과 주소를 대조한다. 필요한 명령 경로와 두 서비스의 active를 확인한다. inactive 또는 명령 누락은 10.2에서 준비한다.

[C10-02] kt66 VM · ccc 호스트 셸
ls -ld는 디렉터리 자체의 존재·권한을 본다. is-enabled는 부팅 시 자동 시작 설정을 확인하며 active와 별개이다. iptables -S는 패킷 처리 규칙을 읽는다. INPUT은 호스트로 들어오는 패킷의 체인, KT66-PERIMETER는 kt66의 사용자 체인이다.

ls -ld ~/book10-state
sudo ls -l /etc/osquery
systemctl is-enabled osqueryd wazuh-agent
sudo iptables -S INPUT
sudo iptables -S KT66-PERIMETER
확인: book10-state가 있으면 기존 기록을 확인하고 새 이름을 정한다. 체인이 없을 때의 오류와 서비스·파일의 초기 상태를 적는다.

[C10-03] kt66 VM · ccc 호스트 셸
mkdir는 디렉터리를 만들며 -m 700은 소유자만 접근하도록 한다. cp -p는 파일과 권한·시각을 보존해 복사한다. sha256sum은 내용의 SHA-256 해시를 출력한다. 줄 끝 역슬래시(\)는 다음 줄을 같은 명령으로 잇는다.

mkdir -m 700 ~/book10-state
sudo cp -p /var/ossec/etc/ossec.conf \
~/book10-state/ossec.conf.before
sudo sha256sum /var/ossec/etc/ossec.conf
확인: 백업 파일이 생성됐는지 ls -l로 확인하고 해시를 기록한다. 이후 설정을 바꾼 경우에만 이 백업으로 원상복구한다.

[C10-04] kt66 VM · ccc 호스트 셸
cat은 파일 내용을 표준 출력으로 읽는다. 첫 파일은 적용 중인 설정, 두 번째는 책의 기준 커밋에 포함된 설정 원본이다.

sudo cat /etc/osquery/osquery.conf
cat ~/kt66/deployment/osquery-linux.conf
확인: schedule 안의 kt66_listening_ports와 kt66_authorized_keys, interval 60을 확인한다. 첫 파일이 없을 때만 다음 복사를 수행한다.

[C10-05] kt66 VM · ccc 호스트 셸
install은 지정한 권한으로 파일을 복사한다. 0644는 소유자 읽기·쓰기, 나머지 읽기 권한이다. --config_path는 검사할 설정, --config_check는 설정 검사이다.

sudo install -m 0644 \
~/kt66/deployment/osquery-linux.conf \
/etc/osquery/osquery.conf
sudo osqueryi \
--config_path=/etc/osquery/osquery.conf --config_check
확인: 검사가 오류 없이 끝나야 한다. 기존 설정 파일이 있는 환경에서는 먼저 별도로 백업하고 필요한 schedule 항목만 병합한다.

[C10-06] kt66 VM · ccc 호스트 셸
sed는 텍스트에서 지정 범위를 출력한다. -n은 자동 출력을 끄고, 쉼표 앞뒤 검색식이 시작·끝 줄이며 p는 출력이다. 작은따옴표는 셸 해석을 막고 \/는 검색식 안의 슬래시 문자이다. grep -n은 줄 번호, -F는 정규표현식 없이 문자열 그대로 찾는 옵션이다.

sudo sed -n '/<wodle name="osquery">/,/<\/wodle>/p' \
/var/ossec/etc/ossec.conf
sudo grep -n -F '/var/log/kern.log' \
/var/ossec/etc/ossec.conf
확인: osquery 블록은 disabled=no, run_daemon=no여야 한다. kern.log를 읽는 localfile도 확인한다.

[C10-07] kt66 VM · ccc 호스트 셸
nano는 터미널 파일 편집기이다. 기존 osquery 블록을 아래 내용과 대조하여 수정한다. kern.log localfile이 없으면 ossec_config의 닫는 태그 앞에 추가한다. Ctrl+O와 Enter로 저장하고 Ctrl+X로 닫는다.

sudo nano /var/ossec/etc/ossec.conf
확인: 같은 osquery 블록이나 kern.log 수집 항목을 중복으로 추가하지 않는다. 주소·등록 정보 등 나머지 설정은 유지한다.

[C10-08] kt66 VM · ccc 호스트 셸
두 Wazuh 실행 파일의 -t는 설정 검사이다. 모두 오류 없이 끝난 뒤 start로 osqueryd를 시작하고 restart로 에이전트를 재시작한다.

sudo /var/ossec/bin/wazuh-logcollector -t
sudo /var/ossec/bin/wazuh-modulesd -t
sudo systemctl start osqueryd
sudo systemctl restart wazuh-agent
systemctl is-active osqueryd wazuh-agent
확인: 두 서비스가 active인지 확인한다. 설정 검사 실패 시 재시작을 멈추고 표시된 태그·경로를 고친다. 재시작 직후에는 초기 조회가 끝나도록 기다린다.

[C10-09] kt66 VM · ccc 호스트 셸
tail -n 3은 파일 끝의 세 줄을 읽는다. grep -E는 확장 정규표현식이며 작은따옴표 안의 파이프(|)는 세 검색식 중 또는(OR)이다. 셸 명령 사이의 출력 전달 기호와 구분한다.

sudo tail -n 3 /var/log/osquery/osqueryd.results.log
sudo grep -n -E \
'netstat|<alias>|<frequency>' \
/var/ossec/etc/ossec.conf
확인: JSON의 name·columns·action과 갱신 시각을 확인한다. netstat listening ports 별칭과 frequency 360을 확인한다.

[C10-10] kt66 VM · ccc 호스트 셸
ss는 소켓 정보를 보여 준다. -l은 리스닝, -n은 주소·포트를 숫자로 표시, -t는 TCP, -p는 프로세스 정보이다. 작은따옴표의 sport = :31337은 로컬 포트 조건이다.

sudo ss -lntp 'sport = :31337'
확인: 표 머리글만 나오면 해당 포트의 TCP 리스너가 없다. 기존 프로세스가 나오면 종료하지 말고 다른 빈 실습 포트를 정한다.

[C10-11] kt66 VM · ccc 호스트 셸 · 터미널 A
-l은 연결 대기, -k는 연결이 끝나도 계속 대기하는 옵션이다. IP는 연결을 받을 로컬 주소, 31337은 포트이다. 터미널 A에서 실행한 채 둔다.

nc -lk 192.168.0.107 31337
확인: 프롬프트가 돌아오지 않는 상태가 정상이다. Address already in use는 포트 충돌이다. 새 명령은 터미널 B에서 입력한다.

[C10-12] kt66 VM · ccc 호스트 셸 · 터미널 B
터미널 B에서 같은 소켓 조회를 반복해 생성 전후를 대조한다.

sudo ss -lntp 'sport = :31337'
확인: LISTEN, 192.168.0.107:31337, nc와 PID를 기록한다. 10.7의 비교가 끝날 때까지 터미널 A를 유지한다.

[C10-13] kt66 VM · ccc 호스트 셸
ps는 프로세스 정보를 읽는다. -p 뒤를 방금 확인한 PID로 바꾼다. -o는 출력 열로, pid·ppid는 자신과 부모 번호, user는 사용자, lstart는 시작 시각, args는 명령줄이다.

ps -p 181571 -o pid,ppid,user,lstart,args
확인: 제시한 사례에서는 ccc가 실행한 nc였다. PID는 재사용되므로 해당 시점의 시작 시각·실행 파일·사용자를 함께 대조한다.

[Q10-01] Windows · Discover · wazuh-alerts-*
리스닝 목록이 바뀐 경보를 조사 대상 호스트로 좁힌다.
콜론(:)은 필드 조건이고 AND는 두 조건을 모두 만족하는 기록을 찾는다. 에이전트 이름은 자기 환경의 값으로 바꾼다.
agent.name:"kt66-host" AND rule.id:533
확인: 6분 주기가 한 번 이상 지난 뒤 **Refresh**한다. 행을 펼쳐 full_log와 previous_output을 비교한다.

[Q10-02] Windows · Discover · wazuh-alerts-*
현재·이전 출력에서 실습 포트의 등장과 사라짐을 비교한다.
별표(*)는 앞뒤에 다른 문자가 있어도 31337이 포함된 값을 찾는다. 괄호 안의 OR는 현재 또는 이전 출력 중 하나에 포트가 있는 조건이다.
agent.name:"kt66-host" AND rule.id:533
AND (full_log:*31337* OR previous_output:*31337*)
확인: 현재 출력에만 있으면 새로 관찰된 리스너, 이전 출력에만 있으면 사라진 리스너 후보이다. 주변 행의 주소와 프로토콜도 대조한다.

[Q10-03] Windows · Discover · wazuh-alerts-*
9장에서 다룬 audit의 명령 실행 경보를 같은 기간에 찾는다.

agent.name:"kt66-host"
AND rule.groups:audit_command
AND data.audit.command:nc
확인: EXECVE의 인수와 PID·PPID·auid를 읽어 소켓의 PID와 대조한다. execve 성공은 nc 실행에 관한 정보이며 포트 연결 성공이나 악성 판정은 별도로 확인한다.

[C10-14] kt66 VM · ccc 호스트 셸
kt66의 방화벽 규칙과 공격자 VM으로 향하는 경로를 확인한다.
iptables -S로 INPUT에서 사용자 체인으로 이동하는 규칙과 체인 내부 순서를 읽는다. ip -4 route get은 상대 주소로 나갈 IPv4 경로를 표시한다. dev 뒤는 네트워크 인터페이스이다. cat으로 실행할 kt66 스크립트 내용을 먼저 확인한다.
sudo iptables -S INPUT
sudo iptables -S KT66-PERIMETER
ip -4 route get 192.168.0.108
cat ~/kt66/deployment/perimeter.sh
확인: 기준 코드의 체인은 기존 연결과 적용 당시의 리스닝 포트를 RETURN 처리하고 나머지 TCP SYN을 LOG 뒤 DROP한다. 예시 인터페이스는 ens33이다.

[C10-15] kt66 VM · ccc 호스트 셸
현재 방화벽 규칙을 보존한 뒤 누락된 실습용 체인을 준비한다.
iptables-save는 현재 규칙을 텍스트로 출력한다. 꺾쇠(>)는 그 출력을 파일에 저장하며 같은 이름이 있으면 덮어쓴다. bash는 확인한 스크립트를 실행한다.
sudo iptables-save > ~/book10-state/iptables.before
sudo bash ~/kt66/deployment/perimeter.sh
sudo iptables -S INPUT
sudo iptables -S KT66-PERIMETER
확인: 현재 SSH 포트가 RETURN 예외에 있는지, LOG의 접두 문자열이 DROP 인지, 마지막 SYN DROP이 있는지 확인한다. 적용 시각과 새로 만든 체인임을 적는다.

[C10-16] kt66 VM · ccc 호스트 셸
rsyslog는 시스템 메시지를 파일로 기록하는 서비스이다. tail로 커널 로그 파일을 읽을 수 있는지도 확인한다.

sudo tail -n 3 /var/log/kern.log
확인: rsyslog가 active이고 파일이 존재해야 한다. 파일에 DROP이 아직 없는 것은 스캔 전이라면 정상일 수 있다.

[C10-19] 공격자 VM · att 셸
-sT는 TCP 연결 스캔, -Pn은 별도 호스트 발견 검사를 생략하고 대상이 응답한다고 가정하는 옵션이다. -n은 이름 조회를 생략한다. -p 1-1000은 포트 범위, --max-retries 1은 탐색 재전송의 상한이다.

확인: Nmap 종료 때까지 기다린다. 이 실습에서 허가된 대상 한 대의 주소인지 확인한다. -Pn의 Host is up 표시를 독립적인 생존 확인 결과로 읽지 않는다.

[C10-20] kt66 VM · ccc 호스트 셸

[C10-23] kt66 VM · ccc 호스트 셸
INPUT에서 이번에 추가한 정확한 규칙을 먼저 확인한다.
-D는 그 규칙 삭제, -i는 들어오는 인터페이스, -j는 이동 대상이다. -F는 지정 체인의 규칙 비우기, -X는 비어 있고 참조되지 않는 사용자 체인 삭제이다. ens33은 자기 환경 값으로 바꾼다.
sudo iptables -S INPUT
sudo iptables -D INPUT -i ens33 -j KT66-PERIMETER
sudo iptables -F KT66-PERIMETER
sudo iptables -X KT66-PERIMETER
sudo iptables -S INPUT
확인: INPUT이 사전 기록과 같은지 확인한다. 다른 체인 이름을 넣거나 체인 이름을 생략해 전체 규칙을 비우지 않는다.

[C10-24] kt66 VM · ccc 호스트 셸

[S10-01] kt66 VM · sudo osqueryi의 osquery> 프롬프트
SELECT는 출력 열, FROM은 조사 표이다. l과 p는 표의 짧은 이름이다. JOIN ... USING(pid)는 pid가 같은 두 행을 연결한다. WHERE는 조건, IN은 괄호 안 값 중 하나를 선택한다. 세미콜론(;)은 SQL 문장의 끝이다.

SELECT p.pid, p.name, p.path, l.address, l.port
FROM listening_ports l
JOIN processes p USING (pid)
WHERE l.port IN (31337,31338);
확인: 현재 열어 둔 31337 행의 nc·실행 파일 경로·주소·PID를 ss와 대조한다. 31338은 10.7에서 만든 뒤 다시 조회한다.

[S10-02] kt66 VM · sudo osqueryi의 osquery> 프롬프트
마침표로 시작하는 .schema는 SQL 문장이 아니라 osqueryi의 표 구조 확인 명령이다. 뒤에는 표 이름을 넣는다.

확인: authorized_keys의 uid·algorithm·key·options·comment·key_file, users의 uid·username을 확인한다.

[S10-03] kt66 VM · sudo osqueryi의 osquery> 프롬프트
u와 k는 users와 authorized_keys의 별칭이다. 이 조회의 CROSS JOIN과 USING(uid)는 각 사용자 uid에 해당하는 키를 읽도록 연결한다. >=는 이상, OR는 둘 중 하나이다. 따라서 UID 1000 이상 계정과 UID 0을 선택한다.

SELECT u.username, k.key_file,
       k.algorithm, k.comment
FROM users u
CROSS JOIN authorized_keys k USING (uid)
WHERE u.uid >= 1000 OR u.uid = 0;
확인: 현재 조회에서는 등록된 키의 사용자·파일·알고리즘·주석을 읽는다. 10.7의 등록 뒤 book10-key@attacker 행을 찾는다.
