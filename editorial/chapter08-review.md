## 슬라이드에서 수정·보완한 해석

1. 무제한 반복 대신 후보 수·병렬 수·timeout을 명시했다. 존재하지 않는 계정 시험은 실제 부재를 먼저 확인한 세 이름으로 제한했다. 원래 목록에 있는 흔한 이름을 곧바로 미존재 계정이라고 가정하지 않았다.
2. `MaxAuthTries`는 한 SSH 연결의 인증 시도 제한이다. Wazuh의 frequency·firedtimes 또는 계정 전체의 누적 실패 횟수와 다르다. 상관 규칙의 시간 창에 이전 시험이 포함될 수 있음을 설명했다.
3. rsyslog의 `message repeated` 요약에는 개별 이벤트와 같은 srcip·dstuser 필드가 없을 수 있다. data.srcip 필터만으로 전체 실패 흐름을 찾지 않도록 원문 검색을 추가했다. 사설 IP도 조사에서 제외하지 않는다.
4. 5710의 잘못된 사용자 이름은 srcuser에서, 정상 계정 인증 대상은 dstuser에서 확인했다. 원문·프로그램 이름·디코더 이름·경보 규칙을 서로 구분했다.
5. 실패 뒤 성공은 계정 탈취의 단독 증거가 아니다. 승인된 작업, 소유자, NAT·공유 계정, 인증 방식, 세션·출발지 포트, 후속 행위를 조사하도록 했다.
6. root 실습의 `kill -HUP 1` 대신 확인 가능한 `service ssh reload`를 사용했다. 설정과 암호 상태를 모두 백업·비교·복구한다. `passwd -l root`만으로 끝내면 바뀐 암호 해시가 남는 문제를 바로잡았다. 전체 shadow 복구는 다른 계정 변경이 없는 실습 구간이라는 전제를 명시했다.
7. root의 5715는 해당 시점의 인증 성공이다. 검색 0건은 root 정책이 안전하다는 증거가 아니다. PermitRootLogin no와 prohibit-password도 구분했다.
8. `sudo -i id`는 로그인 환경에서 id를 실행한 뒤 돌아온다. 계속 root 셸에 머무르는 것으로 설명하지 않았다. 실제 COMMAND는 `/bin/bash --login -c id`였다.
9. shadow의 원래 출력 예시는 해시를 공개하지 않도록 `/dev/null`로 바꿨다. 리디렉션은 호출한 셸이 처리하므로 sudo의 COMMAND에는 `/usr/bin/cat /etc/shadow`만 남는다. 명령 허용 기록만으로 최종 성공을 단정하지 않는다.
10. 5403은 Wazuh의 FTS(최초 관찰) 상태에 영향을 받는다. decoder.ftscomment가 생애 최초 실행을 뜻하지 않는다. 이번 기록에는 명령 필드가 없는 sudo PAM 경고에도 5403이 적용되어 원문 대조가 필요했다.
11. 새 계정은 암호 잠금 상태로 유지했다. sudo 그룹 추가만으로 SSH 재접속이나 ccc 전용 NOPASSWD 규칙의 상속을 주장하지 않는다. usermod에는 이 시험에서 독립적인 그룹 변경 경보가 없어 sudo COMMAND와 auth.log, id·getent를 연결했다.
12. 계정 삭제는 설치된 규칙과 실제 결과의 5903으로 수정했다. 5904는 사용자 정보 변경이며 삭제 규칙이 아니다. 삭제 경보의 srcuser는 삭제 대상이고, 요청자는 앞선 sudo 원문에서 찾는다. userdel 프로그램과 open-userdel 디코더도 구분했다.
13. 생성 경보의 data.shell에는 `/bin/bash,`처럼 구분 쉼표가 포함됐다. 실제 셸 경로는 getent와 원문의 shell 항목으로 확인하도록 설명했다.

## 실행 검증의 한계

저자용 원격 자동화는 제한 시간을 적용해 결과를 기록했다. 독자용 원고는 컨테이너에 직접 들어가 한 명령씩 실행하고 exit로 나오는 절차다. 저자 기록의 일회성 docker exec나 SSH 원격 명령을 독자용 실행 방식으로 옮기지 않았다.

56개 명령 블록 모두에 대해 복사용 파일과 원고의 일치, Bash 구문 분석을 검사했다. 이는 56개 블록 전체의 대화형 입력을 그대로 재연했다는 뜻이 아니다. 특히 Vim의 키 입력·대화형 passwd 프롬프트는 직접 조작하여 검증하지 않았다. 저자 시험에서는 동등한 설정을 sed·chpasswd로 구성한 뒤 유효 설정·로그인·원상복구를 검증했다. 본문의 Vim 절차는 활성 줄을 정확히 찾고 cc로 줄 전체를 교체하도록 정적 검토했다. VM 설치, 운영 환경의 격리 정책 변경, 실제 사고 대응의 차단·자격 증명 폐기는 이번 시험 범위가 아니다.

## 조판과 시각 검토

부크크 B5 Word 원본의 페이지 크기·여백·gutter·테마를 상속했다. OOXML 환산 크기는 188.03×263.03mm이며 본문 영역은 반올림하여 127×192mm이다. 본문 부크크 명조 Light 10.5pt, 제목 부크크 고딕 Light, 코드 Consolas를 사용했다. 표 문자는 검정이며 테두리와 간격을 단순하게 정리했다. 긴 URL은 문자를 추가하거나 생략하지 않고 경로 구분자 뒤에서 줄을 나눴다.

문서 스킬의 render_docx.py는 이 Windows 환경에 soffice.exe가 없어 실패했다. 대체 경로로 설치된 Word COM의 읽기 전용 열기·PDF 내보내기를 사용하고 pypdfium2로 페이지 PNG를 렌더했다. 임시 PDF와 QA 이미지는 build 아래에만 두며 배포하지 않는다.

58쪽 전체를 펼친 지면 이미지로 육안 검사했다. 마지막 수정 뒤 21개 변경 지면(6, 7, 12, 30~34, 37~42, 44, 47, 52, 53, 56~58)을 다시 확인했다. 나머지 37쪽은 앞서 확인한 렌더와 픽셀이 같았다. 잘린 명령·URL, 표의 넘침, 겹침, 빈 그림, 제목만 남는 페이지는 발견하지 못했다. 화면 핵심 필드와 도식 글자를 최종 지면에서 확인했다. 최종 검사 수치는 `chapter08-validation.json`에 기록했다.

7개 도식은 관계·흐름·상태 변화만 표현한다. 인물 삽화는 기존 `assets/illustrations/chapter04/field-check.png`와 `assets/illustrations/chapter06/log-review.png`를 각각 현장 점검·로그 대조 문맥에 재사용했다. 새 인물 이미지는 생성하지 않았다.

## 원상복구와 저장소 포함 범위

root 설정·shadow의 백업 비교와 원래 L 상태, PermitRootLogin no, 새 root 인증 거부, ccc의 정상 접속을 확인했다. 이후 컨테이너 안의 이번 백업 두 개를 삭제했다. book08-user와 동명 그룹·홈을 삭제했고 sudo 그룹의 기존 ccc만 남은 것을 확인했다. 자동 대응의 임시 차단은 해제됐다. 공격자의 이번 후보 파일과 저자 전용 known_hosts 파일을 삭제한 뒤 빈 작업 디렉터리를 제거했다. Hydra는 후속 실습용 준비 도구로 남겼다. 조사 로그·Wazuh 경보는 보존했다.

증거 파일은 위 시험에 필요한 명령·결과·95개 인증 경보·실제 UI로 한정했다. shadow 원문과 암호 해시는 저장소로 가져오지 않았다. 공개 원고에는 실습 환경의 예제 계정·암호만 사용하며 GitHub 인증 토큰은 포함하지 않는다. 검증용 임시 스크립트·세션·PDF·페이지 PNG는 배포 파일에 포함하지 않는다.
